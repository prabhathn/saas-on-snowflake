Data Harmonization and Entity Resolution

Deduplicating records across multiple sources and matching entities when attributes don't line up -- identity resolution for domains, IPs, hashes, and assets where the same entity appears differently in each system.

How Companies Accomplish This Today

  • ETL pipelines with hardcoded rules: Custom scripts that normalize field names, deduplicate on exact matches, and merge records. Breaks when a new source uses a different attribute naming convention.
  • Identity resolution vendors: LiveRamp, Datavant, or specialized identity graphs for people. For non-people entities (domains, IPs, hashes), custom solutions are required.
  • Master Data Management (MDM) tools: Informatica, Reltio, or custom MDM platforms. Heavy, expensive, and not designed for high-velocity security or operational data.
  • Manual reconciliation: Analysts manually review and merge duplicate entities. Doesn't scale beyond a few thousand records.

Roles and People Involved

Data Engineering

Builds the harmonization pipelines: normalization, deduplication, and merge logic that run as data arrives from each source.

Domain Experts

Defines matching rules: "these two domain names refer to the same entity," "this hash variant maps to this malware family." Provides the business logic for fuzzy matching.

Data Architecture

Designs the entity resolution model: identity graphs, canonical entity tables, and the mapping between source-specific identifiers and canonical IDs.

Product / Analytics

Consumes the harmonized data. Needs confidence that "example.com" in source A and "example-domain.com" in source B are the same entity.

Challenges Today

  • Attribute mismatch: Source A calls it "domain_name", source B calls it "hostname", source C calls it "fqdn". Same concept, different attribute names. Normalization is tedious and error-prone.
  • Fuzzy matching at scale: "example.com" vs. "www.example.com" vs. "example-domain.com" vs. "EXAMPLE.COM". Exact dedup misses these. Fuzzy matching (Levenshtein, Jaro-Winkler, semantic similarity) is computationally expensive at billions of rows.
  • Confidence scoring: When two records might be the same entity, you need a confidence score. "80% match" -- is that good enough to merge? Business rules vary by use case.
  • Identity graph maintenance: The mapping between source-specific IDs and canonical entity IDs is itself a graph that grows and evolves. New sources add new identifier types.
  • Deduplication vs. enrichment: Sometimes the same entity appearing in two sources isn't a duplicate -- it's an opportunity to enrich. Source A has the domain's DNS records, source B has its threat classification. Merge, don't dedup.

What Snowflake Offers

  • SQL-native deduplication: QUALIFY + ROW_NUMBER for exact-match dedup. Dynamic tables for continuous dedup as new data arrives. No external pipeline needed.
  • Fuzzy matching with AI functions: AI_SIMILARITY for semantic matching of entity names. "example.com" and "example-domain.com" get a high similarity score without exact string matching.
  • Identity graph in relational tables: Model the identity resolution graph as an EDGES table (source_id, source_system, canonical_id, confidence). Query with standard SQL. No graph database required for the identity layer.
  • Canonical entity tables: Maintain a CANONICAL_ENTITIES table with the resolved entity and a SOURCE_ENTITIES table with the raw records. JOIN to get the full picture: one canonical entity, many source representations.
  • Continuous harmonization: Dynamic tables that re-run harmonization as new source data lands. The canonical entity table is always current without batch jobs.

Snowflake Features Used

QUALIFY + Window Functions

SQL-native deduplication: partition by entity attributes, rank by confidence/source priority, keep the best record. Runs in a dynamic table for continuous operation.

AI_SIMILARITY

Semantic similarity scoring between entity names. Catches "example.com" vs "example-domain.com" that exact matching misses. Runs as a SQL function -- no external service.

MERGE / Upsert

Continuously update the canonical entity table as new source records arrive. MERGE handles insert (new entity) and update (enrich existing) in one operation.

Dynamic Tables for Continuous Resolution

The harmonization pipeline runs as a dynamic table that refreshes automatically. No batch job, no orchestrator. Canonical entities are always current.

Identity Graph Tables

Two tables: CANONICAL_ENTITIES (resolved, deduplicated) and SOURCE_ENTITIES (raw, with source_system and confidence). JOIN to trace any source record to its canonical identity.
