Online Feature Serving and ML UDFs

Deploying models as SQL functions: feature store for consistent inputs, UDF-based inference, and real-time scoring without external infrastructure.

How Companies Accomplish This Today

  • Separate feature stores: Feast, Tecton, or custom Redis-backed stores that maintain real-time and batch features. Yet another system to manage and keep in sync.
  • Model serving endpoints: SageMaker endpoints, Vertex AI, or self-hosted TorchServe/Triton. Add latency, cost, and a network hop for every prediction.
  • Batch scoring only: Run predictions on the full dataset periodically and store results. Predictions are always stale by the time they're used.
  • Feature/serving skew: Features computed differently in training (warehouse SQL) vs. serving (application code). The #1 cause of ML model degradation in production.

Roles and People Involved

ML Engineers

Deploy models to serving infrastructure, manage feature pipelines, and ensure training/serving consistency.

Backend Engineers

Integrate predictions into the product -- call scoring endpoints, handle latency requirements, and manage fallbacks.

Data Engineers

Maintain feature pipelines that compute and materialize features for both training and real-time serving.

Platform / DevOps

Manages the model serving infrastructure: endpoint scaling, GPU allocation, health monitoring, and A/B routing.

Challenges Today

  • Training/serving skew: Features computed with SQL in the warehouse during training are re-implemented in Python/Java for serving. Subtle differences cause prediction quality to degrade.
  • Latency requirements: Real-time scoring (recommendations, fraud detection) needs <50ms responses. Model serving endpoints add network hops and serialization overhead.
  • Feature freshness: Online features should reflect the latest user behavior, but keeping a feature store synchronized with the source of truth is expensive.
  • Infrastructure cost: Always-on model serving endpoints (GPU instances) are expensive even during low-traffic periods.

What Snowflake Offers

  • Feature store with unified compute: Define features once as SQL/Python transformations. Same definitions serve both training and inference -- eliminating training/serving skew entirely.
  • Models deployed as UDFs: Call model predictions directly in SQL. No external endpoint, no network hop, no serialization. Predictions run where the data is.
  • Cortex fine-tuning: Fine-tune foundation models on your data directly in Snowflake. Deploy as a function callable from any query.
  • Batch + real-time in one system: Score the entire customer base in a scheduled batch, or score a single row inline with a query. Same function, different invocation patterns.

Snowflake Features Used

Feature Store

Define feature views as SQL transformations over source tables. Snowflake materializes and refreshes them automatically. Same definition used in training and inference.

Python UDFs / UDTFs

Deploy scikit-learn, XGBoost, or PyTorch models as SQL-callable functions. Vectorized UDFs process batches efficiently. Run predictions inline with any query.

Model Registry Deployment

Deploy a specific model version from the registry as an inference function. Swap versions atomically. Roll back instantly if metrics degrade.

Cortex Fine-Tuning

Fine-tune LLMs on your domain data (classification, extraction, summarization). Deploy the fine-tuned model as a Cortex function callable from SQL.

External Functions

For complex model serving scenarios: call external endpoints (custom model servers) from SQL. Snowflake handles batching, retries, and authentication.
