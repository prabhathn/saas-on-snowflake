AI Functions in the UI

Enriching your product's interface with AI: classifying tickets, summarizing transcripts, extracting fields from documents, and analyzing sentiment, all as SQL function calls. No model hosting, no API keys, no inference infrastructure.

How Companies Accomplish This Today

  • Direct LLM API calls from the backend: Application code calls OpenAI/Anthropic APIs for each AI enrichment. Requires managing API keys, rate limits, retries, and cost tracking per feature.
  • Batch processing pipelines: Nightly jobs that run AI enrichments on new records. Users see AI-generated content only the next day.
  • Embedded third-party AI widgets: Drop-in components (Cohere, AWS Comprehend, Google NLP) that add latency, cost, and data-residency concerns.
  • No AI enrichment: Users manually read full transcripts, hand-classify tickets, and scan documents for key information. Time-consuming and inconsistent.

Roles and People Involved

Product Designers

Decides where AI enrichments add value in the UI: what to summarize, classify, or extract, and how to present AI-generated content alongside source data.

Backend Engineers

Integrates AI function calls into the data pipeline or dynamic tables. No new microservice needed; it's a SQL column.

Frontend Engineers

Renders pre-computed AI output: sentiment badges on tickets, extracted fields in forms, summaries next to source documents.

Data / AI Team

Evaluates AI quality, tunes prompts via AI Function Studio, and monitors output accuracy. Uses the create → evaluate → optimize lifecycle.

Challenges Today

  • Integration complexity: Each AI capability (summarize, classify, extract) requires its own API integration, error handling, and cost tracking. Three features = three microservices.
  • Latency at query time: Calling external LLM APIs adds 1-5 seconds per request. Unacceptable for UI interactions that should feel instant.
  • Cost unpredictability: Token-based pricing makes AI feature costs hard to predict. A verbose transcript costs more to summarize than a short one.
  • Data governance: Sending customer data to external AI APIs raises compliance concerns: data residency, PII exposure, model training opt-out.
  • Quality consistency: Different models, prompts, and context windows produce inconsistent results. No systematic way to evaluate and optimize.

What Snowflake Offers

  • AI as SQL functions: Call AI_CLASSIFY, AI_EXTRACT, AI_COMPLETE, AI_SENTIMENT directly in SQL queries. No API integration, no external service, no data movement.
  • Every modality: Text, documents, images, audio, and video; one function signature, one platform. Classify a PDF, extract fields from a scanned invoice, transcribe a call recording.
  • Pre-compute and cache: Run AI functions in a dynamic table to pre-enrich records as they arrive. UI queries hit pre-computed results. Instant response, no LLM latency at page load.
  • Data never leaves Snowflake: AI functions run inside the platform. Customer data stays in your Snowflake account. No external API calls, full governance retained.
  • Create → Evaluate → Optimize: AI Function Studio (in Cortex Code) drafts prompts, scores against ground truth, and optimizes model/prompt combinations automatically.
  • Granular cost controls: Function-level RBAC, per-user quotas, tag-based budgets, and low-latency spend enforcement. AI credits tracked in CORTEX_USAGE and attributable to tenants.

Classify Tickets Instantly

One SQL call classifies each ticket into your routing categories. No training data, no model fine-tuning; just pass your categories as an array.

Multi-label mode returns all applicable labels, so a billing complaint that's also urgent gets both tags.

SELECT
  ticket_id,
  subject,
  AI_CLASSIFY(
    body,
    ['billing', 'technical', 'feature_request',
     'account', 'praise', 'urgent'],
    { 'output_mode': 'multi' }
  ) AS categories
FROM support_tickets;

Score Sentiment and Extract Key Fields

Add sentiment scoring and structured extraction in the same query. AI_SENTIMENT returns a score from -1 to +1. AI_EXTRACT pulls out specific fields you define.

The extracted JSON becomes queryable structured data. Filter by urgency, join on product area, aggregate by month.

SELECT
  ticket_id,
  AI_SENTIMENT(body) AS sentiment,
  AI_EXTRACT(
    body,
    { 'issue_type': 'string',
      'affected_feature': 'string',
      'requested_action': 'string',
      'repeat_issue': 'boolean' }
  ) AS extracted
FROM support_tickets;

Decision: Live Query or Pre-Enrich?

Steps 2-3 ran AI functions at query time — great for exploration and ad-hoc analysis. For production, you need to decide: call AI live per-request, or pre-compute results into a table?

Most SaaS products end up with pre-enrichment for read-heavy features (ticket queues, dashboards) and live calls for interactive actions (on-demand summarize, user-triggered classify).

Pre-Enrich (Dynamic Table)
Best for: features that display AI results on page load
  • Ticket queue with pre-computed categories, sentiment, summary
  • Dashboard with enriched metrics (avg sentiment by week)
  • Search index built on AI-extracted fields
  • Latency: ~0ms at page load (pre-computed)
  • Cost model: AI runs once per record, regardless of how many times it's viewed
  • Freshness: Controlled by TARGET_LAG (1 min to 1 hour typical)
Live Query (On-Demand)
Best for: user-triggered actions on specific records
  • "Summarize this call" button — runs AI on the one transcript the user clicked
  • Ad-hoc analysis: "Classify all tickets from last week by a custom category set"
  • Translate a document into the user's language on demand
  • Latency: 1-10 seconds depending on input size and model
  • Cost model: AI runs every time the action is triggered
  • Throughput: Subject to concurrent query limits and model availability
Throughput considerations: AI functions consume warehouse credits and are subject to model concurrency limits. For high-volume pre-enrichment (10k+ records/hour), use a dedicated warehouse and consider batching with INSERT...SELECT rather than a dynamic table if you need to control exactly when enrichment runs. Monitor via CORTEX_AI_FUNCTIONS_USAGE_HISTORY.

Pre-Enrich with a Dynamic Table

Wrap the AI functions in a dynamic table so enrichment runs continuously as new tickets arrive. The UI queries pre-computed columns. Zero LLM latency at page load.

Set TARGET_LAG to control freshness. 1 minute means new tickets are enriched within 60 seconds of creation.

CREATE OR REPLACE DYNAMIC TABLE enriched_tickets
  TARGET_LAG = '1 minute'
  WAREHOUSE = AI_WH
AS
SELECT
  ticket_id,
  tenant_id,
  subject,
  body,
  created_at,

  -- Pre-computed AI enrichments
  AI_CLASSIFY(body,
    ['billing', 'technical', 'feature_request',
     'account', 'praise', 'urgent'],
    { 'output_mode': 'multi' }
  ) AS categories,

  AI_SENTIMENT(body) AS sentiment,

  AI_EXTRACT(body, {
    'issue_type': 'string',
    'affected_feature': 'string',
    'requested_action': 'string'
  }) AS extracted,

  AI_COMPLETE('claude-sonnet',
    'Summarize this support ticket in one
     sentence: ' || body
  ) AS summary

FROM support_tickets;

The Product UI

Your frontend queries the dynamic table. No AI calls at render time. Every ticket arrives pre-classified, pre-scored, pre-summarized.

The query is just a SELECT with filters. The intelligence is in the data, not the application code.

-- The frontend query: no AI, just a SELECT
SELECT ticket_id, subject, categories,
       sentiment, summary
FROM enriched_tickets
WHERE tenant_id = 'acme'
  AND created_at > DATEADD('day', -7, CURRENT_DATE())
ORDER BY sentiment ASC;
-- Angriest tickets first

Cost Governance

Control who can use which functions, set per-user quotas, and track AI spend per tenant. Function-level RBAC ensures the support team can classify but can't run expensive completions.

This ties directly to 1.2 Unit Cost Attribution; AI credits show up in the same CORTEX_USAGE views.

-- Function-level RBAC: restrict which roles can use which functions
REVOKE USE AI FUNCTIONS ON ACCOUNT FROM ROLE PUBLIC;

GRANT USE AI FUNCTION AI_CLASSIFY
  ON ACCOUNT TO ROLE support_role;
GRANT USE AI FUNCTION AI_SENTIMENT
  ON ACCOUNT TO ROLE support_role;

-- Only the AI team gets AI_COMPLETE (most expensive)
GRANT USE AI FUNCTION AI_COMPLETE
  ON ACCOUNT TO ROLE ai_team_role;

-- Model-level RBAC: restrict expensive models
CALL SNOWFLAKE.MODELS.CORTEX_BASE_MODELS_REFRESH();
GRANT APPLICATION ROLE
  "CORTEX-MODEL-ROLE-CLAUDE-4-5-SONNET"
  TO ROLE ai_team_role;

-- Track AI spend per tenant
SELECT
  PARSE_JSON(query_tag):'tenant_id' AS tenant,
  function_name,
  SUM(credits_used) AS ai_credits
FROM snowflake.account_usage
  .cortex_ai_functions_usage_history
WHERE start_time > DATEADD('day', -30, CURRENT_DATE())
GROUP BY 1, 2
ORDER BY ai_credits DESC;
