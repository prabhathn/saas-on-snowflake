Unified Semantic Layer

Building a logical entity model that abstracts physical schemas: semantic views for cross-domain relationships, metric definitions, and a single access layer for analytics, agents, and APIs.

How Companies Accomplish This Today

  • dbt metrics layer: Define metrics in YAML, build models in SQL. Good for BI but not accessible to AI agents or APIs directly.
  • Headless BI tools: Cube.dev, Looker, or custom semantic layers that sit between the warehouse and consumers. Another system to maintain.
  • View-based abstraction: Create SQL views that abstract underlying tables. Fragile, no metadata, no natural language descriptions for AI.
  • No abstraction: Every consumer (BI tool, API, AI agent) writes its own SQL against raw tables. Duplication, inconsistency, and no governance.

Roles and People Involved

Analytics Engineering

Defines the semantic model: entities, relationships, metrics, and dimensions. The "data product owner" for the logical layer.

Data Engineering

Maintains the physical tables and pipelines that the semantic layer abstracts. Ensures freshness and quality.

AI / Product Teams

Consumers of the semantic layer: agents use it for natural language queries, APIs use it for structured access, dashboards use it for analytics.

Domain Experts

Provide the business definitions: what "revenue" means, how "active user" is defined, what relationships exist between entities.

Challenges Today

  • Cross-domain entity models: When entities span multiple physical schemas (e.g., a "Customer" that exists in CRM, billing, and support systems), defining a single logical view is complex.
  • Relationship traversal: "Show me everything related to this indicator" requires multi-hop joins across 5+ tables. No standard way to express these relationships in a semantic layer.
  • AI accessibility: Existing semantic layers (dbt, Cube) weren't designed for LLM consumption. No natural language descriptions, no relationship metadata, no tool-use format.
  • Single source of truth: When metrics are defined differently in BI, APIs, and AI, you get different numbers for the same question. Trust erodes.
  • Schema evolution: Physical schemas change. The semantic layer must absorb these changes without breaking downstream consumers.

What Snowflake Offers

  • Semantic views as the universal access layer: One definition of entities, metrics, and relationships. Consumed by SQL queries, Cortex Agents, REST APIs, and BI tools -- all from the same definition.
  • Natural language descriptions: Every metric, dimension, and table has a human-readable description. Cortex Agents use these to translate natural language questions into accurate SQL.
  • Relationship-aware: Define how entities relate (Customer -> Orders -> Products). Agents and queries can traverse relationships without knowing the physical join keys.
  • Cross-domain unification: A semantic view can span tables from different schemas, databases, and even external Iceberg tables. One logical model, multiple physical sources.
  • Verified queries (VQRs): Define and verify canonical queries for common questions. Agents use VQRs as trusted patterns, improving accuracy and reducing hallucination.

Snowflake Features Used

Semantic Views

Declarative YAML/SQL definitions of tables, metrics, dimensions, and relationships. Include natural language descriptions for AI consumption.

Verified Query Representations (VQRs)

Pre-verified canonical queries for common questions. Agents use these as trusted patterns instead of generating SQL from scratch.

Cortex Analyst Integration

Semantic views are the backbone for Cortex Analyst (text-to-SQL). The descriptions and relationships drive accurate query generation.

Cortex Agent Tool Use

Semantic views exposed as tools to Cortex Agents. The agent calls the semantic view tool to query structured data from natural language.

REST API Access

Semantic views accessible via REST API. Your product backend can query the semantic model programmatically without writing raw SQL.
