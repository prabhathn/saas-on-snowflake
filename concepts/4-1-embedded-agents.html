Embedded Agents

Giving your users a conversational AI interface: either fully managed with the Cortex Agent API, or using Snowflake's Cortex REST API as the inference layer for third-party agent frameworks like LangChain or LangGraph.

How Companies Accomplish This Today

  • Build with OpenAI/Anthropic APIs directly: Custom agent frameworks (LangChain, CrewAI) with hand-coded tool definitions. 3-6 months of engineering for a production agent.
  • Third-party copilot platforms: Tools like Glean, Moveworks, or custom GPT wrappers. Data must be exported or API-connected, governance is external to the data platform.
  • Chatbot-only (no tool use): Simple RAG chatbots that can answer questions but can't take actions or query live data. Limited utility for power users.
  • No AI at all: Many SaaS products still rely on search bars, manual reports, and documentation wikis for user self-service.

Roles and People Involved

AI / ML Engineering

Designs the agent's capabilities, defines tools, manages prompt engineering, and evaluates response quality.

Product Engineering

Integrates the agent into the product UI, handles streaming responses, and manages the conversation state.

Data Engineering

Creates semantic views and data models that the agent can query. Ensures data quality and freshness for agent-accessible tables.

Security / Compliance

Ensures the agent respects tenant boundaries, PII handling policies, and can't be prompted to reveal unauthorized data.

Challenges Today

  • Data access governance: Agents need access to data but must respect tenant boundaries. Traditional frameworks have no built-in multi-tenant awareness.
  • Accuracy and grounding: Agents hallucinate when they don't have access to the right data. Ensuring answers are grounded in actual database records is difficult.
  • Infrastructure complexity: Running agent frameworks requires vector databases, embedding services, model hosting, and orchestration: 5+ systems to deploy and maintain.
  • Cost unpredictability: Token costs scale with usage. Without attribution to tenants, AI costs become an unmanageable line item.
  • Tool definition maintenance: As your product evolves, agent tools must be updated. Schema changes break tool definitions silently.

What Snowflake Offers

Two approaches to embedding agents, depending on your needs:

Method 1: Fully Managed

Cortex Agent API

A complete, managed agent runtime. Define tools (semantic views, Cortex Search, custom functions) and Snowflake handles orchestration, tool calling, and response streaming.

  • Built-in multi-tenant governance via row-access policies
  • Semantic views translate natural language to governed SQL
  • Cortex Search provides RAG retrieval as a tool
  • No infrastructure to manage; call via REST
  • Best for: teams that want to ship fast without managing agent orchestration
Method 2: Bring Your Own Framework

Cortex REST API as Inference Layer

Use Snowflake's Cortex REST API (AI_COMPLETE endpoint) as the LLM inference backend for LangChain, LangGraph, or any agent framework. Your orchestration, Snowflake's models.

  • Keep your existing LangChain/LangGraph agent logic
  • Swap OpenAI/Anthropic with Cortex REST API; data never leaves Snowflake
  • Full control over tool definitions, routing, and conversation state
  • Access to Snowflake-hosted models (Llama, Mistral, etc.) at Snowflake-managed scale
  • Best for: teams with existing agent investments who want Snowflake as the inference + data layer

Snowflake Features Used

Semantic Views

Business-friendly data models that describe tables in natural language. Cortex Agents use these to translate user questions into accurate, governed SQL.

Semantic search over unstructured data. Used as a retrieval tool by agents for RAG-grounded answers over docs, tickets, and knowledge bases.

Policies enforce tenant isolation on agent-generated queries. The agent sees only what the calling tenant is allowed to see. No custom filtering code.

Create a Semantic View

Define a semantic view over your ORDERS and CUSTOMERS tables. This gives the agent a structured, described interface to your data: metrics, dimensions, and relationships the agent can reason about.

CREATE OR REPLACE SEMANTIC VIEW saas_analytics_sv
  TABLES (
    orders_t AS app_db.serving.orders
      PRIMARY KEY (order_id)
      COMMENT = 'Customer orders with revenue data',
    customers_t AS app_db.serving.customers
      PRIMARY KEY (customer_id)
      COMMENT = 'Customer profiles and metadata'
  )
  RELATIONSHIPS (
    orders_t (customer_id) REFERENCES customers_t
  )
  DIMENSIONS (
    orders_t.product   AS orders_t.product_name
      COMMENT = 'Product name',
    customers_t.region AS customers_t.region
      COMMENT = 'Geographic region',
    orders_t.order_date AS orders_t.created_at
      COMMENT = 'Date of order'
  )
  METRICS (
    orders_t.total_revenue AS SUM(orders_t.amount)
      COMMENT = 'Total revenue in dollars',
    orders_t.order_count AS COUNT(orders_t.order_id)
      COMMENT = 'Number of orders placed',
    orders_t.avg_order_value AS AVG(orders_t.amount)
      COMMENT = 'Average order value in dollars'
  );

Create the Agent

Define a Cortex Agent with two tools: the semantic view for structured data queries and a Cortex Search service for unstructured knowledge retrieval. One SQL statement gives you a production agent.

CREATE OR REPLACE AGENT support_agent
  COMMENT = 'Customer-facing analytics assistant'
  FROM SPECIFICATION
  $$
  models:
    orchestration: auto

  instructions:
    response: "You are a helpful analytics assistant
      for a SaaS platform. Answer questions about the
      user's data using the analyst tool. For product
      questions, search the help documentation.
      Always cite your data sources."

  tools:
    - tool_spec:
        type: "cortex_analyst_text_to_sql"
        name: "analytics_tool"
        description: "Query customer orders and
          revenue data. Use for revenue, order count,
          and product performance questions."
    - tool_spec:
        type: "cortex_search"
        name: "help_docs_search"
        description: "Search product help docs
          and knowledge base articles. Use for how-to
          and feature questions."

  tool_resources:
    analytics_tool:
      semantic_view: "app_db.agents.saas_analytics_sv"
    help_docs_search:
      search_service: "app_db.agents.help_docs_svc"
      max_results: "5"
  $$;

Multi-Tenant Isolation

The key insight: pass the tenant context directly in the agent:run API call via the variables block. Snowflake sets immutable session attributes before any SQL executes, and the Row Access Policy (RAP) filters rows based on those attributes.

No separate query needed. No prompt engineering for filters. The agent-generated SQL runs unmodified; data isolation is enforced at the engine level via SYS_CONTEXT.

Flow: Your app authenticates the user → resolves their tenant_id → passes it as an immutable variable in the agent:run call → RAP filters transparently.

How It Works
Your App
passes tenant_id in the agent call
-- POST /api/v2/databases/app_db/schemas/agents/agents/support_agent:run
{
  "messages": [{"role": "user", "content": "What's our revenue?"}],
  "variables": {
    "tenant_id": {
      "value": "acme",
      "type": "string",
      "is_immutable_session_attribute": true
    }
  }
}
↓ Snowflake sets session attribute before SQL runs
Agent SQL
No tenant filter; same for everyone
-- Agent-generated (identical for all tenants)
SELECT SUM(amount) AS total_revenue
FROM orders
WHERE created_at >= '2026-04-01';
↓ RAP intercepts at engine level
Row Access Policy
reads immutable session attribute
CREATE ROW ACCESS POLICY rap_tenant
  AS (tenant_col STRING) RETURNS BOOLEAN ->
    tenant_col = SYS_CONTEXT(
      'SNOWFLAKE$SESSION_ATTRIBUTES',
      'tenant_id'
    );
variables: tenant_id = "acme"
Same SQL → $1.24M
3,241 rows (only Acme)
variables: tenant_id = "globex"
Same SQL → $892K
2,107 rows (only Globex)

Knowledge Base + Fuzzy Matching

Cortex Search serves two purposes as an agent tool:

1. Document retrieval (RAG): When the user asks a product question, the agent searches help docs and generates a grounded answer with citations.

2. Fuzzy matching for high-cardinality columns: When the user says "show me Acme's orders" but the database stores "Acme Corporation Inc.", Cortex Search resolves the fuzzy match to the correct canonical value before the SQL runs. Critical for customer names, product SKUs, or region codes where users never type the exact DB value.
