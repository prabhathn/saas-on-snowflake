Unit Cost Attribution

Pinpointing the cost of serving each tenant: warehouse isolation, query tagging, ACCOUNT_USAGE views, resource monitors, and AI-spend attribution.

How Companies Accomplish This Today

  • Proportional allocation: Divide total infrastructure bill by number of tenants or by revenue share. Inaccurate -- a 1-user tenant may consume more than a 100-user tenant.
  • Warehouse-per-tenant: Give each customer their own compute cluster. Accurate but expensive (idle costs) and operationally complex beyond ~50 tenants.
  • Log analysis and sampling: Parse query logs, correlate with tenant IDs, and estimate cost attribution after the fact. Delayed, approximate, and fragile.
  • Custom metering infrastructure: Build a sidecar system that tracks every API call, query, and storage operation per tenant. 6-12 months of engineering.

Roles and People Involved

Finance / FP&A

Needs per-customer COGS to calculate gross margins, identify unprofitable accounts, and inform pricing decisions.

Platform Engineering

Instruments queries with tenant context, manages warehouse allocation, and builds cost attribution pipelines.

Product Management

Uses cost data to validate pricing tiers, identify features that are expensive to serve, and design usage-based pricing.

Executive Leadership

Needs unit economics visibility for board reporting, investor conversations, and strategic decisions about which segments to pursue.

Challenges Today

  • Attribution accuracy: Shared infrastructure (caches, indexes, background jobs) makes it hard to assign costs to specific tenants with confidence.
  • AI cost opacity: LLM inference, embedding generation, and agent calls are new cost categories with no established attribution patterns.
  • Delayed visibility: Cost data is often only available days or weeks after consumption -- too late to prevent budget overruns.
  • Multi-dimensional costs: A single tenant action (e.g., "generate report") may hit compute, storage, AI inference, and external API costs simultaneously.
  • Granularity vs. overhead tradeoff: Tracking every query to a tenant adds latency and complexity. Most companies settle for estimates.

What Snowflake Offers

  • Native query tagging: Tag every query with tenant_id at the session level. Snowflake records it in QUERY_HISTORY -- no custom logging needed.
  • Credit-level attribution: ACCOUNT_USAGE views break down credit consumption by warehouse, user, and query tag. Map directly to tenants.
  • AI-spend visibility: CORTEX_USAGE tracks token consumption by model, function, and query -- attributable to the same tenant tags.
  • Real-time monitoring: Resource monitors alert when a tenant approaches their credit threshold -- before they overspend, not after.

Snowflake Features Used

Query Tagging

Set QUERY_TAG at session or statement level with tenant_id, feature_name, or any custom metadata. Recorded in QUERY_HISTORY for downstream analysis.

ACCOUNT_USAGE Views

WAREHOUSE_METERING_HISTORY, QUERY_HISTORY, and STORAGE_USAGE provide credit-level granularity. Join with query tags for per-tenant breakdown.

Cortex AI Functions Usage

Tracks token consumption, model invocations, and credit usage for all Cortex AI functions. Has query_tag natively -- no join needed for per-tenant attribution.

Resource Monitors

Set credit limits per warehouse (which maps to tenant or tier). Receive alerts at 75%, 90%, 100% thresholds. Auto-suspend at limit.

Warehouse Isolation

For enterprise tenants, dedicate a warehouse. All queries from that tenant run on their compute -- attribution is exact and performance is isolated.

Budgets

Snowflake Budgets let you set spending limits by custom groups (tenant tier, department). Get alerts before limits are hit.

How These Views Link Together for Per-Tenant Attribution

QUERY_HISTORY is the central join table. Newer Cortex views carry query_tag natively -- no join required for AI cost attribution.

Tag Queries with Tenant Context

Set QUERY_TAG at session level with a JSON payload containing tenant_id and feature. Two approaches: SQL (for any client) or as a connection parameter in your SDK.

-- Option A: SQL (works from any client / SQL API multi-statement)
ALTER SESSION SET QUERY_TAG = '{
  "tenant": "acme",
  "feature": "reporting",
  "tier": "enterprise"
}';

-- Every subsequent query carries this tag automatically
# Option B: Python SDK (set at connection time)
import snowflake.connector
import json

conn = snowflake.connector.connect(
    account="myaccount",
    user="app_service_user",
    password="...",
    warehouse="wh_acme",
    session_parameters={
        "QUERY_TAG": json.dumps({
            "tenant": "acme",
            "feature": "reporting",
            "tier": "enterprise"
        })
    }
)
# All queries on this connection are tagged -- no ALTER SESSION needed

Query ACCOUNT_USAGE for Attribution

Join QUERY_ATTRIBUTION_HISTORY with QUERY_HISTORY to get per-tenant credit consumption. Parse the JSON query_tag to group by tenant, feature, or tier.

SELECT
  PARSE_JSON(qh.query_tag):'tenant'::STRING AS tenant,
  PARSE_JSON(qh.query_tag):'feature'::STRING AS feature,
  SUM(qa.credits_attributed_compute) AS credits,
  COUNT(*) AS query_count
FROM snowflake.account_usage.query_attribution_history qa
JOIN snowflake.account_usage.query_history qh
  ON qa.query_id = qh.query_id
WHERE qa.start_time >= DATEADD(month, -1, CURRENT_DATE())
  AND qh.query_tag IS NOT NULL
GROUP BY tenant, feature
ORDER BY credits DESC;

AI Cost Attribution

CORTEX_AI_FUNCTIONS_USAGE_HISTORY has query_tag natively -- no join needed. Group AI spend by tenant, model, and function directly.

Per-Tenant AI Cost Breakdown
SELECT
  PARSE_JSON(query_tag):'tenant'::STRING AS tenant,
  function_name,
  model_name,
  SUM(credits) AS ai_credits,
  SUM(metrics[0]:'value') AS total_tokens
FROM snowflake.account_usage.cortex_ai_functions_usage_history
WHERE start_time >= DATEADD(month, -1, CURRENT_DATE())
GROUP BY tenant, function_name, model_name;

Resource Monitor Alert

Set a resource monitor on a tenant's warehouse with credit thresholds. Show the alert firing at 90% and auto-suspend at 100%. Prevents surprise overruns.

Tenant Budget Enforcement
CREATE RESOURCE MONITOR acme_monthly
  WITH CREDIT_QUOTA = 100
  FREQUENCY = MONTHLY
  START_TIMESTAMP = IMMEDIATELY
  TRIGGERS
    ON 75 PERCENT DO NOTIFY
    ON 90 PERCENT DO NOTIFY
    ON 100 PERCENT DO SUSPEND;

ALTER WAREHOUSE wh_acme
  SET RESOURCE_MONITOR = acme_monthly;
