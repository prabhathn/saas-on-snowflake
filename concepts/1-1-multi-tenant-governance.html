Multi-Tenant Governance and Provisioning

How to enforce tenant isolation at the data platform layer, so developers write normal SQL, policies are enforced transparently, and cross-tenant data leakage is structurally impossible.

How Companies Accomplish This Today

Most SaaS companies build tenant isolation at the application layer, embedding WHERE clauses in every query, adding middleware to filter results, and relying on developers to never forget a tenant check.

  • Application-layer filtering: Every query includes a tenant_id filter, enforced by ORM middleware or API gateways. One missed filter = data leak.
  • Separate databases per tenant: Physical isolation at the infrastructure level. Safe but expensive, hard to manage at scale, and makes cross-tenant analytics nearly impossible.
  • Custom RBAC frameworks: Home-grown permission systems built on top of PostgreSQL RLS or application-side checks. Requires constant maintenance as the product evolves.
  • Network-level isolation: VPCs or separate clusters per customer segment (enterprise tier). Becomes an operational nightmare beyond a few dozen tenants.

Roles and People Involved

Platform Engineering

Designs the tenancy model, manages database schemas, and enforces isolation guarantees across the stack.

Security / Compliance

Audits access patterns, ensures SOC2/HIPAA compliance, validates that no cross-tenant data exposure is possible.

Application Developers

Must correctly implement tenant filtering in every new feature, endpoint, and background job today. With Snowflake policies, they write normal SQL.

DevOps / SRE

Manages infrastructure isolation (VPCs, clusters, connection pooling) and handles tenant-specific scaling and provisioning automation.

Challenges Today

  • Human error at scale: One developer forgets a tenant filter in a new API endpoint. Instant cross-tenant data leak. This is the #1 cause of SaaS security incidents.
  • Audit complexity: Proving to SOC2 auditors that every single query path enforces isolation requires exhaustive code review and testing.
  • Performance vs. isolation tradeoff: Physical separation (separate DBs) is safe but 10x more expensive. Logical separation (shared tables) is efficient but risky.
  • Feature velocity drag: Every new feature requires re-implementing and re-testing tenant isolation, slowing engineering teams by 20-30%.
  • AI makes it worse: AI agents, LLM-generated SQL, and autonomous copilots create new pathways for cross-tenant exposure. Securing AI features requires additional controls beyond WHERE clauses.

What Snowflake Offers

Snowflake moves tenant isolation from the application layer to the data platform layer, making it structurally impossible, not just unlikely, for a query to return another tenant's data.

  • Guaranteed isolation without performance penalty: Row-access policies enforce tenant boundaries at the engine level, not the application level. No WHERE clause to forget.
  • One shared schema, many tenants: Keep the operational simplicity of a single database while each tenant sees only their data, with no per-tenant infrastructure.
  • Audit-ready by default: Access policies are declarative and centrally managed. Show auditors the policy definition, not thousands of lines of application code.
  • Zero engineering tax on new features: Developers write normal SQL. Policies are enforced transparently. No tenant-aware code required.
  • AI-safe multi-tenancy: Cortex Agents inherit session attributes with is_immutable_session_attribute, so row-access policies apply to AI-generated queries automatically.

The Role Hierarchy in a Multi-Tenant App

A typical SaaS application on Snowflake uses three tiers of Snowflake roles. The row-access policy controls which tenant's rows are visible; the masking policy controls which columns are redacted within that tenant.

PLATFORM_ADMIN Your ops/engineering team (the SaaS provider). Bypasses the row-access policy; sees all tenants. Used for cross-tenant analytics, debugging, provisioning.
TENANT_ADMIN Your customer's admin (e.g., Acme's IT lead). Sees only their tenant's rows, but with full column visibility: unmasked phone numbers, PII, etc.
TENANT_USER Your customer's regular end-users (e.g., Acme's sales reps). Sees only their tenant's rows, and sensitive columns are fully masked: phone numbers, SSNs, etc. are redacted.

In practice, the application's service account (APP_SERVICE_ROLE) sets the tenant session variable at connection time, and your app logic maps the end-user's permissions to the appropriate Snowflake role (TENANT_ADMIN or TENANT_USER).

The First Decision: Combine or Separate Tenants?

Snowflake supports three tenancy patterns. The current guidance is to start with combining tenants and only separate when specific factors require it. Model your data for either approach from day one.

Recommended starting point

Combined Tenants (Shared Tables)

All tenants share the same tables. A tenant_id column stamps every row. Row-access policies and session variables enforce isolation at query time.

  • Scales from tens to millions of tenants
  • Simpler architecture, with fewer objects to manage
  • More cost-efficient (shared compute)
  • Cross-tenant analytics are trivial
  • Requires consistent data model across tenants
Separate when needed

Separated Tenants (Per-Tenant Objects)

Each tenant gets its own database, schema, or table. RBAC controls which user/role can access which objects. Can be combined with shared compute.

  • Unique data models per tenant
  • Contractual/legal isolation requirements
  • Per-tenant encryption keys (Tri-Secret Secure)
  • Direct Snowflake UI access per customer
  • Scales to tens-to-hundreds of tenants

Key principle: Regardless of approach, stamp every row with a tenant identifier. This gives you the flexibility to migrate between models and prepares for Snowflake's future tenant-as-first-class-construct capabilities.

The Second Decision: Tenant-Owned Data or Entitlement-Based Access?

Not every SaaS app works the same way. Some apps store each customer's data separately. Others provide a shared dataset where each customer sees a licensed slice. The row-access policy pattern changes depending on which model you're building.

Classic SaaS

Tenant-Owned Data

Each tenant generates and owns their data. Every row belongs to exactly one tenant. The row-access policy matches tenant_id directly against a session variable.

  • CRM, project management, HR platforms
  • Each customer's data is distinct and private
  • Simple policy: tenant_id = session_var
  • One tenant can never see another tenant's rows
Data-as-a-Service

Entitlement-Based Access

One shared dataset owned by the provider. Each tenant is entitled to a subset based on business attributes: regions, topics, asset classes, feeds. An entitlements table maps tenants to the slices they've licensed.

  • Market data, threat intel, benchmarking, industry analytics
  • Rows don't "belong" to a tenant; tenants get access to subsets
  • Policy joins to an entitlements table on a business key
  • Use memoizable functions for performance at scale

Many apps are a hybrid. Your customers' own data (support tickets, usage logs) follows the tenant-owned model, while shared reference data (product catalog, benchmarks) follows the entitlement model. Both patterns can coexist in the same Snowflake account using different row-access policies per table.

Snowflake Features Used

Row-Access Policies

SQL-defined policies that automatically filter rows based on the querying user's context. Applied once, enforced on every query. No application changes needed.

Dynamic Data Masking

Column-level policies that mask sensitive data differently per role. A support agent sees masked SSNs while an admin sees full values.

Session Variables / SYS_CONTEXT

Set tenant context at connection time. Row-access policies reference SYS_CONTEXT('SNOWFLAKE$SESSION_ATTRIBUTES', 'tenant_id') to filter transparently.

Database Roles and RBAC

Granular, schema-scoped roles that map to SaaS concepts like "tenant admin" or "read-only analyst." Compose via role hierarchy without sprawl.

Object Tagging

Tag tables and columns with metadata (sensitivity level, tenant ownership). Tags drive policy enforcement and simplify governance at scale.

Access History

Full audit trail of who accessed what data, when, and through which policy. Powers compliance reporting and anomaly detection.

Create the Shared Schema

Start with a single ORDERS table containing data for three tenants. Every row has a tenant_id. A superuser can see all rows.

This is the "combine tenants" approach, the recommended starting point.

-- Shared multi-tenant table
CREATE TABLE app_db.serving.orders (
  order_id    INT,
  tenant_id   VARCHAR,
  customer    VARCHAR,
  product     VARCHAR,
  amount      DECIMAL(10,2),
  email       VARCHAR,
  order_date  DATE
);

-- Cluster by tenant_id for efficient pruning
ALTER TABLE app_db.serving.orders
  CLUSTER BY (tenant_id, order_date);

Create the Row-Access Policy

Define a policy that filters rows where tenant_id matches the current session's tenant context. This uses SYS_CONTEXT to read session attributes set by the application.

Key insight: The policy is applied once and enforced on every query against this table; developers never write a WHERE clause for tenant filtering.

-- Create the row-access policy
CREATE OR REPLACE ROW ACCESS POLICY security.tenant_filter
  AS (tenant_col VARCHAR) RETURNS BOOLEAN ->
    -- Match the row's tenant to the session variable
    tenant_col = SYS_CONTEXT(
      'SNOWFLAKE$SESSION_ATTRIBUTES',
      'tenant_id'
    )
    -- Allow platform admins to see all rows
    OR IS_ROLE_IN_SESSION('PLATFORM_ADMIN');

-- Bind the policy to the tenant_id column
ALTER TABLE app_db.serving.orders
  ADD ROW ACCESS POLICY security.tenant_filter
  ON (tenant_id);

Variant: Entitlement-Based Policy

For data-as-a-service apps, the data isn't stamped with a tenant_id. Instead, an entitlements table maps each tenant to the regions (or topics, feeds, etc.) they've licensed.

The memoizable function caches each tenant's entitlements per-session, so the policy lookup doesn't re-execute for every row.

-- Entitlements table: which tenants see which regions
CREATE TABLE security.entitlements (
  tenant_id  VARCHAR,
  region     VARCHAR
);
-- Acme licensed NA + EU; Globex licensed APAC only
INSERT INTO security.entitlements VALUES
  ('acme', 'NA'), ('acme', 'EU'),
  ('globex', 'APAC');

-- Memoizable function for performance
CREATE FUNCTION security.allowed_regions()
  RETURNS ARRAY MEMOIZABLE AS
  'SELECT ARRAY_AGG(region) FROM security.entitlements
   WHERE tenant_id = SYS_CONTEXT(
     ''SNOWFLAKE$SESSION_ATTRIBUTES'', ''tenant_id'')';

-- Row-access policy using entitlements
CREATE ROW ACCESS POLICY security.region_entitlement
  AS (region_col VARCHAR) RETURNS BOOLEAN ->
    ARRAY_CONTAINS(region_col::VARIANT,
      security.allowed_regions())
    OR IS_ROLE_IN_SESSION('PLATFORM_ADMIN');

-- Apply to the shared market data table
ALTER TABLE app_db.serving.market_data
  ADD ROW ACCESS POLICY security.region_entitlement
  ON (region);

Application Sets Tenant Context

The application tier authenticates via key-pair auth, then sets the tenant session variable before issuing queries. Same SQL, different context, different results.

Users never know Snowflake exists. They authenticate to your app, and your app handles the Snowflake connection.

# Python application tier
import snowflake.connector

def get_orders(tenant_id: str):
    conn = snowflake.connector.connect(
        account="myaccount",
        user="APP_SERVICE_USER",
        private_key=load_key_from_secrets(),
        role="APP_SERVICE_ROLE",
        warehouse="APP_WH",
        database="APP_DB",
        session_parameters={
            "tenant_id": tenant_id  # Set session var
        }
    )
    # No WHERE tenant_id = ... needed!
    # The row-access policy handles it.
    cur = conn.cursor()
    cur.execute("SELECT * FROM serving.orders")
    return cur.fetchall()

Add Dynamic Masking

Apply a masking policy on the PHONE column: full visibility for tenant admins, area-code-only for standard users. Different roles within the same tenant see different levels of detail.

This layers on top of row-access policies; you get both row-level and column-level control.

-- Masking policy: full phone for admins, area code only for others
CREATE OR REPLACE MASKING POLICY security.phone_mask
  AS (val VARCHAR) RETURNS VARCHAR ->
    CASE
      WHEN IS_ROLE_IN_SESSION('TENANT_ADMIN')
        THEN val
      ELSE '***-***-****'
    END;

-- Apply to the phone column
ALTER TABLE app_db.serving.orders
  ALTER COLUMN phone
  SET MASKING POLICY security.phone_mask;

AI-Safe Multi-Tenancy

When calling Cortex Agents, pass the tenant ID as an immutable session attribute. The agent can't override it; row-access policies apply to all AI-generated SQL.

This is critical: without immutable attributes, a prompt injection could trick the agent into changing the tenant context.

// Cortex Agent API call with tenant isolation
POST /api/v2/databases/APP_DB/schemas/AGENTS
     /agents/support_agent:run

{
  "messages": [{
    "role": "user",
    "content": "Show my recent orders"
  }],
  "variables": {
    "tenant_id": {
      "value": "acme",
      "type": "string",
      "is_immutable_session_attribute": true

Automated Provisioning

Wrap tenant onboarding in a stored procedure. When a new customer signs up, call one procedure that sets up their role, mapping table entry, and default configuration.

No manual SQL, no human error. The procedure is the template; every tenant gets the same setup.

CREATE OR REPLACE PROCEDURE admin.provision_tenant(
  p_tenant_id VARCHAR,
  p_admin_email VARCHAR
)
RETURNS VARCHAR
LANGUAGE SQL
EXECUTE AS CALLER
AS
BEGIN
  -- 1. Create tenant-specific role
  CREATE ROLE IF NOT EXISTS IDENTIFIER(:p_tenant_id || '_ROLE');

  -- 2. Grant access to serving schema
  GRANT USAGE ON DATABASE app_db
    TO ROLE IDENTIFIER(:p_tenant_id || '_ROLE');
  GRANT USAGE ON SCHEMA app_db.serving
    TO ROLE IDENTIFIER(:p_tenant_id || '_ROLE');
  GRANT SELECT ON ALL TABLES IN SCHEMA app_db.serving
    TO ROLE IDENTIFIER(:p_tenant_id || '_ROLE');

  -- 3. Register in entitlements table
  INSERT INTO security.tenant_registry
    (tenant_id, admin_email, created_at, status)
  VALUES
    (:p_tenant_id, :p_admin_email, CURRENT_TIMESTAMP(), 'active');

  RETURN 'Tenant ' || :p_tenant_id || ' provisioned';
END;

-- Provision a new tenant in one call
CALL admin.provision_tenant('newcorp', 'admin@newcorp.com');

Audit and Prove

Query ACCESS_HISTORY to show a complete log of who accessed what, proving to auditors that policies are enforced. Demonstrate that no Globex data was ever visible to the Acme session.

This is the "show auditors the policy, not thousands of lines of code" moment.

-- Show all access to the orders table in the last 24h
SELECT
  query_start_time,
  user_name,
  role_name,
  PARSE_JSON(direct_objects_accessed)[0]:'objectName'
    AS table_accessed,
  PARSE_JSON(direct_objects_accessed)[0]:'columns'
    AS columns_accessed,
  policies_referenced
FROM snowflake.account_usage.access_history
WHERE query_start_time > DATEADD('day', -1, CURRENT_TIMESTAMP())
  AND ARRAY_CONTAINS(
    'ORDERS'::VARIANT,
    TRANSFORM(direct_objects_accessed,
      x -> x:'objectName'))
ORDER BY query_start_time DESC;
